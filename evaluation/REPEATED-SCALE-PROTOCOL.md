# Repeated scale and conflicting-update protocol

Recorded before execution, 2 November 2026. Execute unchanged vendored NuggetStore/SqliteStore using SQLite WASM3.53.0, with and without the existing optional composite lookup index. Do not alter previous scale.json or scale-indexed.json.

Five trial seeds:27201–27205. Each trial contains8 cases: original/indexed schema ×1,000/10,000 initial keys ×short/long canonical text. Shuffle the8-case execution order independently per seed and run each case in a fresh Node process. This removes preceding case state from process RSS and balances run order, but does not simulate hardware diversity or independent machines. The complete design contains40 fresh-process cases.

Each case inserts distinct synthetic keys in seeded random order. Short canonical text contains subject/status/value. Long canonical text appends approximately2KiB of descriptive filler with distinct tokens while preserving the same subject/predicate/value and gold. The fact object stays short to prevent long shared text from changing value-deduplication semantics. Record actual byte lengths. After initial insertion, update10% of keys once, in random order. Updates overlap existing validity intervals, use clearly different values and two new source URLs, and have later effective start and observation times. Record conflict outcomes, applied updates and resulting record counts rather than assuming conflicts are resolved correctly.

After initial insertion and after updates, issue200 seeded exact-subject queries each in first and repeated order. Query valid time is after the update. Record each query's latency, predicted value, expected value, returned status and success. Report phase-specific p50/p95/p99, correct target retrieval, insertion and update throughput, per-operation latency tails, process RSS snapshots/peak sampled RSS, exported DB bytes, stored row counts and exact query plans before/after optional configuration. RSS remains a process-level measurement including WASM and cannot be interpreted as database memory alone. DB export is outside timed insert/query phases. "First" means first-query order against an already built in-memory store, not cold disk or browser startup.

For each configuration report median, minimum/maximum and coefficient of variation across5 process trials for total insert/update time, throughput, process RSS and DB size; report median and full observed range of per-run query p95/p99. Preserve all raw timings and failures. No new100k original repeats are planned because previous insertion alone takes~11.5minutes/run; existing100k single-run results remain explicitly descriptive. No model or external runtime calls occur. Environment snapshots and execution order are retained.
